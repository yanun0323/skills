# Multilingual README

Let readers switch languages from any version and find the same complete project information. Use this order: shared cover image → language badges → introduction → documentation sections.

## Check the existing structure

Read the project's root READMEs and inspect related images to identify the languages, filenames, sections, and content sources. Use the source specified by the user; otherwise, use the main README as the translation baseline while preserving accurate information unique to other versions. Resolve conflicting information by checking project configuration or code.

Preserve existing filenames and language coverage. For a new set without specified languages, use these five languages with English as the entry point:

| Language | Filename |
| --- | --- |
| English | `README.md` |
| 繁體中文 | `README-tw.md` |
| 简体中文 | `README-cn.md` |
| 日本語 | `README-ja.md` |
| 한국어 | `README-ko.md` |

When the user requests only one additional language, create that version and update the language navigation in every version.

## Top-of-page layout

When a suitable project cover exists, share it across all versions, default to a height of 160, and link it to the project root. The image path below is an example; use an existing asset. If no cover exists, omit the image and keep the project title.

```html
<a href="."><img height="160" src="./images/cover.png" alt="Project name"></a>
```

Place language badges below the cover. Use the same order, labels, and destinations in every version, including the current language. Label each language in its own language. Put each badge on its own Markdown source line with no blank lines between badges:

```markdown
[![English](https://img.shields.io/badge/English-Click-yellow)](README.md)
[![繁體中文](https://img.shields.io/badge/繁體中文-點擊查看-orange)](README-tw.md)
[![简体中文](https://img.shields.io/badge/简体中文-点击查看-orange)](README-cn.md)
[![日本語](https://img.shields.io/badge/日本語-クリック-blue)](README-ja.md)
[![한국어](https://img.shields.io/badge/한국어-클릭-yellow)](README-ko.md)
```

Adjust badges to match the actual language set. Link only to files that exist or will be created in this task. Use relative paths so links work across branches; adjust paths for READMEs in subdirectories. Use valid English color names or hexadecimal color codes for badges.

## Content and translation

Complete the baseline version first, then translate its sections in the same order. Start with a short paragraph explaining what the project is and what it helps users do. For new content, choose applicable sections such as Installation, Features, Prerequisites, Getting Started, Example, How It Works, Settings, Manual Commands, and More Information. For existing READMEs, preserve useful structure and add only relevant sections supported by project facts.

- Provide complete content in every version, keeping features, steps, default settings, limitations, and examples consistent.
- Use natural local wording. For Traditional Chinese, use common Taiwanese terms such as 檔案, 專案, 儲存, and 預設. Review Traditional and Simplified Chinese separately.
- Preserve code identifiers, configuration keys, package names, paths, commands, and URLs. Keep interface action names as they actually appear in the product; translate the surrounding explanation.
- Keep code behavior identical. Comments may be translated; preserve strings that affect example behavior or expected output.
- Share installation badges, images, and external links. Image alt text may be translated. Section links must target the anchors generated by the headings in that language.
- When synchronizing content changes, update all language versions within scope. If the user limits the edit to one version, respect that scope and report which versions remain unsynchronized.

## Completion checks

Before delivery, verify that:

1. Every language badge points to an actual README, and all versions have the same language list and order.
2. Local images, relative links, and section anchors resolve, and Markdown code fences are closed.
3. Sections correspond across languages, with no missing or conflicting features, steps, settings, or examples.
4. No example placeholders remain, and no features, installation instructions, or URLs have been carried over from an unrelated project.

Finish with a brief list of files created or updated and any information still awaiting confirmation.
